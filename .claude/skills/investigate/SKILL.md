# 修正前の調査

## 手順

1. 依頼から、調査の対象と完了の条件を一文にまとめる。
2. `git status --short` と `git branch --show-current` を確認する。未コミットの変更は壊さない。
3. 前回の続きの作業なら `docs/handoffs/current.md` を読む。関係のない作業なら読まない。
4. `docs/project-map/INDEX.md` の「作業別の入口」から候補ファイルを選ぶ。依存関係や影響範囲を判断する必要があるときだけ `DEPENDENCIES.md` の該当する行を読む。
5. 候補ファイルを読む。大きいファイル（MODULES.md で★が付いたもの）は、まず Grep でシンボルを探し、その周辺だけを読む。
6. 呼び出し元と関連テストを Grep で確認する（例: `Grep "sendCleaningZone" lib test`）。
7. 関係がないと分かったファイルは、それ以上調べない。`lib/` 全体をまとめて読まない。
8. マップと実装が食い違っていたら記録しておく（後で `/project-map` を実行する）。

## 報告の形式

- 確認した事実（ファイル:行 を付ける）
- 原因または実装方針の仮説（推測であることを明記する）
- 関係するファイル
- 影響範囲（DEPENDENCIES.md の該当行と照らし合わせる）
- 必要なテスト（`flutter analyze` / `flutter test test/<file>_test.dart` など）
- 追加で必要な情報

調査の段階ではコードを変更しない。ユーザーが実装まで依頼している場合は、報告のあとに作業計画を示してから実装する。
